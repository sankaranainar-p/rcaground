# Evaluation protocol

This document defines what rcaground measures, how each metric is computed,
and the statistical procedure used when results are reported. Code comments
reference its sections by name.

It was ported from the protocol of the application this toolkit was
extracted from. Sections specific to that application (live remediation,
domain-specific service level indicators, triage classifier training) were
removed; the faithfulness and statistics sections are carried over unchanged
apart from file paths, so that the committed study artefacts under
`docs/faithfulness/` remain interpretable.

## Research questions supported

| ID | Question | Entry point |
|----|----------|-------------|
| RQ1 | How accurately do root cause ranking baselines localise the faulty service on public RCA benchmarks (AC@k, Avg@5)? | `rcaground/bench/run_benchmark.py` |
| RQ2 | What fraction of the claims in an LLM generated RCA explanation are grounded in, and entailed by, the telemetry evidence shown to the model? | `rcaground/bench/run_faithfulness_study.py` |
| RQ3 | How well do automated faithfulness judges agree with human raters (Cohen's kappa)? | `rcaground/bench/build_rating_harness.py` |
| RQ4 | How often does alert synthesis name a service other than the ground truth root cause, and how does that propagate into evidence ranking? | `rcaground/bench/run_faithfulness_study.py` (`mis_synthesised`) |

All questions are evaluated offline against static, pre-labelled RCAEval and
OpenRCA cases. No live system is under test.

## Metric definitions

- **AC@k** — fraction of cases whose ground truth root cause service appears in the top k of a baseline's ranking. **Avg@5** is the mean of AC@1 to AC@5, matched to RCAEval's own definition (see `docs/b2_rcaeval_parity_report.md` for the parity check against RCAEval's BARO implementation).
- **RCA faithfulness** — fraction of an RCA's claims that are (stage 1) grounded in an existing, anomalous evidence pack item AND (stage 2) supported by that evidence per the **primary judge** (see Faithfulness judging below). Reported alongside `dropped_claims` (claims discarded for citing unknown evidence IDs).
- **Alert mis-synthesis rate** — fraction of cases whose synthesized alert names a service other than the ground truth root cause.
- **No reported quantity is derived from a pseudo-random draw.** `tests/test_no_random_in_loop.py` asserts that no module under `rcaground/signals` imports a random number generator, and runs in CI on every commit.

## Faithfulness judging

Two-stage check per claim (`rcaground/bench/faithfulness.py`):

- **Stage 1 — existence + anomaly.** Every cited evidence ID must exist in the A8 evidence pack and have anomaly score ≥ `MIN_ANOMALY_SCORE` (0.3). Deterministic. Gates.
- **Stage 2 — entailment.** Does the rendered evidence support the claim?

Stage 2 uses **two judge backends**, with distinct roles:

| Backend | Model | Role | Gates faithfulness? |
|---|---|---|---|
| **chat-model judge** | `rcaground.bench.faithfulness.DEFAULT_CHAT_JUDGE_DIGEST` (currently `ollama:qwen3.8:27b`) | **Primary.** Its score + threshold define the reported RCA faithfulness metric and are the automated side of the human-agreement (Cohen's κ) study. | **Yes** |
| **NLI cross-encoder** | `cross-encoder/nli-deberta-v3-base` | **Comparison point / documented failure — see the characterization below; it is not a faithfulness judge on this data.** Reported next to the primary judge to quantify the gap; never the headline number. | No |

Rules:

- The chat-judge model **family must differ from the RCA generator's** (`rcaground.agents.rca.RCAAgent.generate` defaults to `ollama:llama3.1`, llama family → judge is qwen family) so the judge is not grading a sibling model's output. If the RCA model changes, the judge model must be re-checked for family separation.
- **Corrected (A20 review):** the chat judge is run **once per claim** (temperature 0), not 5 times as an earlier version of this document stated. Checked directly against `rcaground/bench/faithfulness.py` and the canonical faithfulness run (`docs/faithfulness/judge_scores.jsonl`, generated 20260910T170647Z at git_sha ce9491b1, 67 rows): there is no repeat-calling loop in the code, and the data has exactly one row per distinct `(case_id, claim_text)` pair with no evidence any claim was ever judged more than once. The "5 times, distinct seeds" language was never implemented and is removed rather than justified after the fact; temperature-0 repeats would in any case be pointless against sampling variance and were never motivated as a guard against backend/batching nondeterminism instead. The NLI judge is deterministic and also run once.
- **Truncated / unparseable judge replies are never trusted.** If the model's reply is cut at the token limit (`LLMResponse.truncated`, from Ollama `done_reason == "length"` / OpenAI `finish_reason == "length"`) the call is retried once at 3× the budget; if it is still truncated, or the reply cannot be parsed, the claim's stage-2 result is marked invalid (`stage2_valid == False`). Invalid claims are **excluded** from `stage2_pass_rate` and `avg_faithfulness_score`, counted in `n_stage2_invalid`, and count as not-faithful for `overall_faithful_rate`. A non-trivial `n_stage2_invalid` is reported as a run limitation.
- **NLI score is raw `P(entailment)`** from the 3-class head.
- **What the NLI judge can and cannot do (probed, `tests/test_faithfulness.py::test_nli_capability_*`):** on general-language pairs its entailment head works normally ("a man playing guitar on stage" ⊨ "a person performing music" → P(entail) ≈ 0.98). On this task it recognises a claim only when the claim is **at most one lexical / directional substitution away from the evidence's literal text** — "spiked to 100.0" ⊨ "rose to 100" / "CPU increased" / "reached 100 percent" / "experienced high CPU usage" (all P(entail) > 0.9). It **cannot** do the abstractive or multi-hop step that essentially every real RCA claim requires:
  - naming a failure mode the evidence implies but does not state — "was saturated", "was fully utilised", "had a memory leak", "is a bottleneck" → `neutral`, P(entail) ≈ 0 (even though it separately accepts "100 percent" ⊨ "saturated" — it will not chain "spiked to 100.0" → "100 percent" → "saturated");
  - interpreting the z-score — `z=108.5` does **not** entail "far above baseline" / "deviated far from its normal range" for this model.
  On our telemetry-notation evidence it therefore behaves as a **shallow restatement detector, not an entailment judge over RCA reasoning**: it scores ~0 for any claim that *characterises* the failure rather than *echoing the metric*. All 10 cases sampled for this study (`docs/faithfulness/`, generated 20260910T170647Z at git_sha ce9491b1) remain **in** the study; `RE1-OB_cartservice_disk_1` is a documented pipeline failure, not an exclusion — its synthesized alert matched an unrelated `currencyservice` memory signal instead of the case's actual `cartservice` disk fault, so evidence ranking returned nothing and the RCA model's resulting claims were all correctly dropped for citing evidence never shown to it (zero claims recorded for this case, contributing nothing to either judge's per-claim numbers — see the `mis_synthesised` finding below for why this is not a one-off). Its mean P(entail) on hand-written, genuinely-grounded paraphrased control claims (n=9, drawn from the 9 cases that produced usable evidence) was **0.0014** — indistinguishable from its score on adversarial claims (0.000). This is why it is a comparison point only.
- **Alert mis-synthesis (`mis_synthesised`, A20 review) — outranks the faithfulness pass-rate number below.** `rcaground/bench/run_faithfulness_study.py` now counts, for every case, whether the synthesized alert's matched service (`Alert.service`) equals the case's ground-truth `root_cause_service` (an alert can only be scored this way outside `rcaground/signals/alert_synth.py` itself, since that module structurally never receives `GroundTruth` — see its isolation-invariant docstring). Measured directly against the 10 real RE1-OB study cases (`data/rcaeval/RE1-OB`, reproducible via `synthesize_alert`): **8 of 10 cases mis-synthesise** — the alert names a service other than the ground-truth root cause (e.g. `RE1-OB_cartservice_cpu_1`'s ground truth is `cartservice`, the synthesized alert matched `redis`). Only 2 of 10 (`checkoutservice_cpu_1`, `currencyservice_loss_1`) matched the correct service. `RE1-OB_cartservice_disk_1`'s zero-claim failure above is not an outlier; it is the one case out of eight where the mismatch also broke evidence ranking downstream. Plainly: **the alert-synthesis step names the wrong service before RCA ever runs in the majority of cases studied**, which is a pipeline-reliability finding independent of and more consequential than the RCA faithfulness pass-rate reported below — a faithful-to-evidence RCA claim can still be reasoning about the wrong service's evidence pack. This is expected in a microservices system where faults cascade (a naive earliest-breach alert will often catch a downstream symptom before the upstream root cause breaches), but it was previously undocumented outside one case, and is now tracked and reported for every run of the faithfulness study rather than surfaced only when it happens to also zero out a case's claims.
- **Alert mis-synthesis confirmed at scale, and scoped against A7/A8 (A20 review).** The 8/10 rate above is not specific to this small study sample: measured against the full 340-case A7 train/val/test pool (training report in the upstream application repository), RE1-OB (125 cases) mis-synthesises at 89.6% and RE2-TT (90 cases) at 97.8% — combined, **200/215 = 93.0%** on the two datasets where per-service attribution is actually possible. RE1-SS (125 cases) reads 100% but is excluded from that figure: its raw Prometheus column names (e.g. `carts_container-cpu-system-seconds-total`) never match `rcaground/signals/rcaeval.py`'s `_METRIC_COL_RE`, so every RE1-SS metric falls back to a synthetic `"cluster"` service regardless of alert correctness — a data-adapter gap, not evidence about alert-synthesis behaviour, and a separate, pre-existing limitation of its own. The evidence-ranker's critical-path boost (`EvidenceRanker.boost_graph_path`, see A8) is keyed to this same mis-attributed alert service, though it is architecturally inert for RE1-OB/RE1-SS (no trace-derived topology exists for either — neither dataset ships a `traces.csv`) and empirically changes ranked output in 17.8% of RE2-TT cases (16/90, measured by comparing boosted vs. unboosted ranked evidence packs), with no consistent directional bias toward or away from the correct metric family. The faithfulness study reported above is built entirely on RE1-OB cases, which carry no trace data and therefore have zero exposure to this boost-leak channel — its faithfulness numbers are not confounded by it, even though the alert-synthesis mis-attribution itself still is (see above).
- It does retain **high precision on contradictions and unrelated claims** (both → P(entail) ≈ 0), so a *high* NLI score is still meaningful (near-verbatim support); a *low* one is not (could be fabrication, could be a true abstractive claim).
- **NLI scores are never averaged into a faithfulness statistic** — a low one carries zero information. `compute_faithfulness_metrics` computes `avg_faithfulness_score` / `stage2_pass_rate` / `overall_faithful_rate` from the **chat judge only** (all `None` with a caveat if no chat-judge scores are present). NLI enters exactly one aggregate, `nli_corroboration_rate`: the fraction of chat-faithful **production** claims (`kind=='rca'`; control/adversarial claims are judge-calibration probes, excluded from this denominator) that NLI *independently* scores ≥ `NLI_CONFIRM_THRESHOLD` (0.8) — a one-directional corroboration signal. The same computation over all populations is retained for reference as `nli_corroboration_rate_all_populations`, never cited as the primary figure. The earlier `0.5·(1 + P(entail) − P(contra))` blend was rejected for parking every `neutral` claim at the 0.5 pass/fail threshold; an interim `avg_entailment_score` that averaged NLI's ~0s into a reported mean was likewise removed.
- Judge outputs are stored as `results/faithfulness/<ts>/judge_scores.jsonl` (one record per `(case_id, claim_text)`, both judges' scores + raw output + model digests) plus `manifest.json`. `results/` is gitignored, so these per-run directories are ephemeral scratch output, not citable artefacts. The run this document cites is committed at `docs/faithfulness/{judge_scores.jsonl,manifest.json}` (`manifest.json.git_sha` records which commit produced it — currently ce9491b1); re-running the study does not move this citation forward until the committed copy is deliberately replaced. The human-rating study joins on `(case_id, claim_text)` to compute κ **against the chat judge**; NLI agreement is reported as a secondary comparison.

## Statistical procedure

- Significance threshold: **alpha = 0.05**.
- All pairwise comparisons within a given RQ's family of comparisons use **Holm–Bonferroni correction** across that full family, controlling family-wise error rate (A20 review: widened from "pairwise comparisons across LLM configurations," which as stated would have excluded the ablation family, e.g. the A1–A6 system-variant comparisons in `rcaground/bench/run_benchmark.py`, and the baseline family from correction). This covers, per RQ: LLM-configuration comparisons (e.g. Groq vs. Ollama, or prompt variant A vs. B), ablation comparisons, and baseline comparisons alike — whichever family of comparisons that RQ's analysis actually runs.
- LLM components are called once per case at temperature 0; no repeat averaging is performed, and no between-repeat variance is reported.
- Reported effect sizes accompany every significance test (Cohen's d for continuous metrics, Cohen's h for proportions such as accuracy).
- Paired tests (Wilcoxon signed-rank) are used when comparing two configurations on the same case set; unpaired tests (Mann-Whitney U) are used only when case sets differ (e.g. RCAEval vs. OpenRCA).
